# Куда поедем?

Совместное планирование поездок: общий на всех участников чек-лист мест с
ссылками на карты, ценами, датами, временем и фотографиями. Из точек строится
маршрут в Яндекс.Картах или Google Maps.

Счета делятся на участников — поровну, на выбранных или своими суммами (общий
счёт в ресторане, где каждый ел на своё). Из счетов собирается свод «кто кому
должен» с минимальным числом переводов.

Домен: `trip.burninghouse.ru`. Аккаунты — общие, через
[BurningHouse Auth](../Auth/INTEGRATION.md); своих логинов и паролей у сервиса нет.

## Что внутри

| Файл | Что это |
|---|---|
| `server.js` | весь бэкенд: SQLite, API, отдача статики |
| `auth-client.js` | проверка токена по JWKS (копия из `Auth/client/`) |
| `index.html` | разметка приложения |
| `assets/app.js` | вся логика фронта |
| `assets/styles.css` | токены Material 3 и компоненты |
| `assets/receipt.js` | разбор чека, вставленного текстом |
| `assets/ocr.js` | распознавание чека по фотографии |
| `assets/vendor/` | **единственный** чужой код: tesseract.js и русская модель |
| `assets/brand.css`, `assets/brand.js` | фирменный слой — **копии**, правят их в `Shared/` |
| `test/e2e.mjs` | сквозная проверка: поднимает auth и сервис сама |
| `test/receipt.mjs` | разбор чека на настоящих формах строк |

Серверных зависимостей нет вовсе: SQLite — встроенный `node:sqlite`, поэтому ни
`npm install`, ни `node_modules` здесь не бывает. Нужен Node 24 (на Node 22
работает с флагом `--experimental-sqlite`). Единственный чужой код — движок
распознавания чека в `assets/vendor/`, он лежит копией и загружается браузером
только когда человек действительно фотографирует чек.

## Локальный запуск

Одной командой — поднимает auth и сервис, регистрирует клиента и заводит
тестовый аккаунт:

```bash
node dev.mjs
```

Открывать `http://localhost:8790`, входить как `dev` / `dev-parol-2026`.
Начать с чистых данных — `node dev.mjs --reset`. Всё живёт в `.dev/` и не
коммитится; репозиторий `Auth` должен лежать рядом.

### Почему Live Server не подходит

Три причины, и каждой достаточно:

1. **Это не статика.** Данные, проверка токена и отдача фотографий — в
   `server.js`. Без него страница получит 401 на первом же запросе.
2. **`redirect_uri` сверяется побайтово.** Live Server отдаёт на порту 5500, а в
   auth зарегистрирован `http://localhost:8790/` — вход отобьётся ещё до формы.
3. **Кука сессии auth помечена `Secure`** и по `http://` браузером не
   сохраняется. Поэтому auth локально запускают с `DEV=1`; без него вход вроде
   бы проходит, но возвращает на исходную, будто ничего не было. `dev.mjs`
   ставит этот флаг сам.

### Руками, если нужно по шагам

```bash
cd ../Auth && node server.js client-add trip "Куда поедем?" http://localhost:8790/
DEV=1 ISSUER=http://localhost:8788 PORT=8788 node server.js
```

```bash
AUTH_ISSUER=http://localhost:8788 PORT=8790 node server.js
```

На Node 22 к обеим командам нужен флаг `--experimental-sqlite` (`dev.mjs`
подставляет его сам).

### Тест

Поднимает оба сервиса сам, порты 8788 и 8790 должны быть свободны:

```bash
node test/e2e.mjs
```

## Деплой

Схема общая для всех проектов BurningHouse: GitHub Actions собирает образ и
пушит в Docker Hub, на сервер не заходит; новый образ забирает Watchtower.
Подробности и установка Watchtower — в `../Auth/README-deploy.md`.

Секреты репозитория: только `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`.
SSH-ключа в CI быть не должно.

Первый выкат на сервере:

```bash
mkdir -p ~/trip && cd ~/trip
# положить сюда docker-compose.prod.yml из репозитория как docker-compose.yml
docker compose up -d
```

Зарегистрировать сервис в auth (иначе на входе будет «сервис не зарегистрирован»):

```bash
cd ~/auth && docker compose exec auth node server.js client-add trip "Куда поедем?" https://trip.burninghouse.ru/
```

`redirect_uri` сверяется побайтово — со слэшем на конце, ровно как здесь.

nginx: готовый конфиг — `deploy/nginx-trip-443.conf`. Единственное, чем он
отличается от соседних сервисов, — `client_max_body_size 8m`: без этого
загрузка фотографий отваливалась бы с 413 ещё до сервиса.

```bash
sudo cp deploy/nginx-trip-443.conf /etc/nginx/sites-available/trip
sudo ln -s /etc/nginx/sites-available/trip /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

## Переменные окружения

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | 8790 | порт |
| `HOST` | 127.0.0.1 | интерфейс (за nginx оставляем localhost) |
| `DATA_DIR` | `./data` | `store.db` и каталог `photos/` |
| `AUTH_ISSUER` | — | **обязательна**; совпадает с `ISSUER` auth символ в символ |
| `AUTH_CLIENT_ID` | `trip` | идентификатор сервиса в auth |
| `AUTH_BASE` | `= AUTH_ISSUER` | куда фронт уводит на вход, если он отличается от внутреннего адреса |
| `AUTH_JWKS_URL` | `AUTH_ISSUER/.well-known/jwks.json` | если auth виден серверу по другому адресу, чем браузеру |
| `AUTH_CLOCK_SKEW` | 30 | допуск на расхождение часов, секунды |
| `MAX_PHOTO_BYTES` | 4194304 | предел на одно фото (уже после сжатия в браузере) |
| `RESOLVE_SHORT_LINKS` | 1 | разворачивать короткие ссылки карт; `0` — не ходить в сеть вовсе |
| `ALLOWED_ORIGIN` | — | CORS; нужен, только если фронт отдаётся с другого домена |

## Как устроены данные

Реляционно, а не одним JSON-блобом: `trips`, `trip_members`, `places`, `photos`.
По этим полям считается смета, строится маршрут и раскладывается по дням —
в блобе это пришлось бы разбирать на каждый запрос. Ключ везде — `user_id` из
токена (стабильный UUID), логин хранится рядом только для подписи в интерфейсе.

Фотографии лежат файлами в `DATA_DIR/photos`, в базе только метаданные:
SQLite с мегабайтными блобами пухнет и перестаёт помещаться в кэш страниц.
Отдаются они по токену, поэтому в `<img src>` их подставить нельзя — фронт
качает их через `auth.fetch` и держит `objectURL` в кэше.

## Что стоит знать при правках

**Фирменные файлы не редактируют здесь.** `assets/brand.css` и `assets/brand.js` —
копии из `../Shared/`; правка уедет при следующем `node Shared/sync.mjs`. Чтобы
не забыть разложить, поставьте хук: `cp ../Shared/pre-commit .git/hooks/pre-commit`.

**Своей страницы входа нет и не планируется.** Аккаунт общий, форма живёт на
auth-домене; экран «нужен вход» показывается только если увести туда не удалось.

**Подписывать человека — `name || username`.** `name` — необязательное имя из
общего кабинета BurningHouse, оно приходит в токене только если человек сам
включил показ. На фронте для этого есть `who(u)`, на сервере имя хранится в
`trip_members.name` и освежается при каждом обращении: включить и выключить
показ можно в любой момент, и сервис обязан это подхватить.

**Координаты из ссылок** разбираются одинаково на сервере и в браузере
(`parseGeo` и `parseGeoClient`). Порядок координат у сервисов разный: у Яндекса
в `ll`/`pt` — «долгота,широта», у Google везде «широта,долгота». Это главный
источник ошибок; проверки на каждый формат есть в `test/e2e.mjs`.

**Короткие ссылки** (`maps.app.goo.gl/…`) разворачивает сервер — строго по
списку хостов и не читая тело ответа. Сервер, который ходит по любому
присланному адресу, — это SSRF, а из контейнера видны и соседние контейнеры,
и метаданные хостинга.

## Счета, долги и переводы

Счёт у места — это `paid_by` (кто платил) и `split`: `equal` или `custom`.
При `equal` доли не хранятся вовсе, а считаются от текущего состава — новый
попутчик автоматически попадает в уже заведённые счета. При `custom` доли лежат
в `place_shares` явно; нераспределённый остаток несёт плательщик, поэтому сумма
всегда сходится. Режим «на выбранных» отдельной сущностью не является: это те же
явные доли, заполненные поровну между отмеченными.

Третий режим — **по позициям** (`split = 'items'`): у места появляется список
позиций чека, каждый отмечает свои, цена позиции делится между отметившими.
Чайник на троих — это позиция, у которой отмечены трое. Никем не разобранная
позиция делится на всех: молча повесить её на плательщика было бы несправедливо.
Пока позиции есть, цена места равна их сумме (`syncCostFromItems`) — иначе смета
считалась бы по одной цифре, а «моя доля» по другой. Чаевые заводят такой же
строкой.

### Распознавание чека

Фотография чека распознаётся **в браузере** (`assets/ocr.js`, движок в
`assets/vendor/`). Наружу не уходит ничего: фото с суммами — не тот файл,
который стоит отправлять постороннему сервису ради удобства. Платные API ФНС
по QR мы не рассматривали, а бесплатных, по сути, нет; к тому же они бесполезны
за границей, где фискальных чеков нет вовсе.

Порядок: уменьшить до 1600 точек по длинной стороне → обесцветить → локальный
порог → Tesseract с русской моделью → текст в тот же построчный разбор →
предпросмотр с правкой. На синтетическом чеке весь путь занимает ~1,7 секунды.

Две вещи, на которых легко обжечься, обе проверены живьём:

- **Глобально растягивать контраст нельзя.** Текста на чеке меньше двух
  процентов площади, и отброс «выбросов» по процентилям выкидывает ровно его —
  распознавание молча возвращает пустую строку. Контраст вытягивает локальный
  порог, глобальный тут вреден.
- **Порог должен быть относительным** (метод Брэдли: темнее среднего по окну на
  15%), а не «темнее на N единиц». На свежем чеке текст почти чёрный, на
  выцветшем светло-серый — абсолютный порог годится ровно для одного из них.

OpenCV намеренно не брали: из его десяти мегабайт понадобилось бы полпроцента,
а нужное — обесцветить и взять локальный порог — это сотня строк на canvas.
Выравнивание наклона пока не делаем; если пойдут кривые снимки, это первое, что
стоит добавить.

Разбор вставленного чека — `assets/receipt.js`, вынесен отдельно ради тестов
(`test/receipt.mjs`). Правила: «2 x 445,00 890,00» → берём сумму; «3 х 180» →
произведение; иначе последнее число в строке. Служебные строки (ИТОГО, НДС, ИНН,
Total, Cash) отбрасываются — «ИТОГО», попавшее в позиции, удваивает счёт. Всё
сомнительное лучше пропустить: пропущенную строку человек допишет, а тихо
переставленную цену заметит только при расчёте.

Свод долгов считается на клиенте (`tripDebts`): баланс каждого = заплатил минус
должен, дальше жадный взаимозачёт от самого большого долга к самому большому
кредиту. Компании нужен ответ «Маша отдаёт Даниле 1 400», а не список из
двадцати чеков.

**Статус перевода банку мы не видим и видеть не можем.** Поэтому `settlements` —
это две отметки людей: отправитель говорит «я перевёл», получатель подтверждает
«получил». Долг гасится сразу после первой отметки, иначе тот, кто честно
перевёл, снова видел бы себя должником; пока подтверждения нет, запись помечена
ожидающей, и убрать её может любая из сторон.

**Телефон получателя** приходит из auth и только с согласия владельца (см.
раздел про телефон в `../Auth/INTEGRATION.md`). Копия лежит в `trip_members.phone`
и освежается при каждом обращении владельца — выключил показ, копия исчезла.
Номер виден только внутри поездки; в превью приглашения его нет.

**Ссылку СБП на перевод между людьми сгенерировать нельзя.** НСПК выдаёт QR и
платёжные ссылки через банк-эквайер по договору — это сценарий для магазинов, а
не для «скинуть другу». В диалоге перевода поэтому: номер крупно, кнопка
скопировать и две кнопки банков — они открывают собственные страницы Сбера и
Т-Банка с уже подставленным номером:

```
https://www.sberbank.ru/ru/choise_bank?requisiteNumber=79001234567&bankCode=100000000111
https://t.tb.ru/c2c-qr-choose-bank?requisiteNumber=+79001234567&bankCode=100000000004
```

**Сумму в них не подставляем намеренно.** Параметр нигде не описан, а угаданное
имя банк молча проигнорирует — человек решит, что сумма уже вписана, и отправит
не ту. Пусть лучше сумма остаётся на экране и копируется явно.
